## 1. 문제 정의

추억이 담긴 옷은 버리기 아깝지만 입지도 않습니다. 이 옷 사진과 사연을 입력하면 MCM 헤리티지와 융합한 **재창조 디자인 3안**을 제안하고, 사용자가 고른 1안을 **3D 굿즈(GLB)·디지털 보증서·제품 큐레이션**으로 만들어 주는 서비스를 기획했습니다.

명품 브랜드는 매장 밖에서 젊은 고객과 만날 접점이 부족합니다. "내 옷이 MCM 제품에 들어가 있다"는 경험이 자연스럽게 매장으로 향하는 발걸음이 되도록 설계했습니다.

## 2. 파이프라인

```
옷 사진 + 사연
  → [1] Claude Sonnet 5 (Vision)  시각 분석 · 사연 해석 · 에디션명 · 보증서 문구
  → [2] Claude Sonnet 5 + 브랜드 자산 RAG   디자인 스펙 3안 (safe / balanced / bold)
  → [3] Gemini 이미지 모델   옷 사진 × MCM 레퍼런스 다중 이미지 융합 → 컨셉 이미지 3장
  → [게이트] Claude Haiku 4.5   스펙 반영 · 브랜드 정합성 · 실현 가능성 · 로고 판독성 병렬 채점
  → 👤 사용자 선택 (선택은 번복되지 않음)
  → [4] Meshy Image-to-3D   GLB + 투명 배경 정면 썸네일
  → [5] Claude Sonnet 5 + 제품 카탈로그   어울리는 MCM 제품 2~3개 추천 + 이유
```

전 구간은 FastAPI REST API로 백엔드에 노출되고, 사용자 선택이 파이프라인 중간에 있어 작업이 `awaiting_selection` 상태에서 멈췄다가 재개되는 비동기 job 상태 머신으로 동작합니다.

## 3. 핵심 설계 판단

### "모델은 제안하고, 하네스가 검증한다"

기술 스택보다 먼저 정한 것은 원칙이었습니다. 실존 브랜드 이름으로 결과물을 내는 서비스에서 존재하지 않는 제품을 지어내거나 브랜드답지 않은 결과물을 내보내면 신뢰가 무너집니다. 그래서 LangChain 같은 프레임워크 대신 **AI를 둘러싼 검증 계층을 직접 구현**했습니다.

### 환각을 프롬프트가 아니라 구조로 차단

"지어내지 마세요"라는 부탁은 방어가 아닙니다. 지어내는 것이 **불가능한 구조**를 만들었습니다.

- **Structured Outputs**: 모든 LLM 호출에 JSON 스키마를 강제합니다. 스키마로 표현할 수 없는 규칙(개수·중복·조합)은 코드 검증으로 넘기고, 위반 사유를 프롬프트에 피드백해 1회 재시도합니다.
- **enum 동적 주입**: 추천 제품 ID를 호출 시점에 카탈로그에서 생성한 enum으로 선언합니다. 존재하지 않는 제품은 생성될 수조차 없습니다.
- **브랜드 자산 RAG**: LLM은 MCM 지식을 신뢰할 수준으로 내장하고 있지 않습니다. 공식 제품 이미지 113종과 디자인 코드 문서를 컨텍스트로 주입하고, 변하지 않는 부분은 프롬프트 캐시에 올려 비용을 낮췄습니다.

### 후보 3안 = 위험 포트폴리오

"후보 3개 만들어"라고 하면 비슷한 것 3개가 나옵니다. **safe(패턴 이식·패치) / balanced(하이브리드) / bold(재구성·굿즈 전환)** 세 위험 수준을 enum과 코드 검증으로 강제하고, 반드시 **단일 호출**로 생성했습니다. 독립 3회 호출은 서로를 몰라 다양성을 보장할 수 없기 때문입니다.

창의성의 코어는 방식이 아니라 **사연↔요소 매핑**입니다. 모든 디자인 요소에 "옷의 무엇을 → 제품의 어디로 → 왜(사연 근거)"를 요구했습니다. "고3 밤 자전거" 사연의 해진 소매는 결함이 아닌 비저블 멘딩 디테일이 되었습니다.

### 계약 우선 개발

AI 파트 두 명이 브랜치를 나눠 병렬로 개발하면서, 단계 간 입출력을 **Pydantic 스키마 파일로 먼저 확정**했습니다. 스키마 하나가 Swagger 문서, 런타임 검증, LLM 출력 강제의 단일 원천이 되어 병합 당일 충돌 없이 맞물렸습니다.

## 4. 막힌 지점과 해결

**심사 AI의 암시 편향.** 생성 이미지에서 로고가 가끔 "MOM"으로 뭉개졌습니다. 게이트에 "MOM이면 탈락" 기준을 넣자 심사 AI가 **모든 이미지에서 MOM을 찾아내기 시작**했습니다. 같은 이미지 점수가 82→48로 흔들리고, 브랜드 코드의 "로렐 잎 좌9·우8"을 근거로 잎 개수를 세어 감점하고, 통과했던 골든 샘플이 42점으로 추락하는 회귀까지 생겼습니다. 판정 대상을 "가장 크게 보이는 로고"로 한정하고 잎 개수 세기를 금지한 뒤, **골든 샘플 벤치마크로 회귀를 측정하며** 기준을 교정했습니다. AI 심사관도 튜닝 대상이라는 것을 배웠습니다.

**설계 간 충돌.** 통합 중 "후보 자리에 생성 실패 2개"라는 제보가 왔습니다. 버그가 아니었습니다. 게이트는 통과 컷만 반환(가변)하고, 비즈니스 모델은 "1번 무료 + 2·3번 잠금 해제"로 항상 3장을 전제했습니다. 모두가 명세대로 옳게 동작한 결과가 사용자에게는 오류로 보였습니다. 탈락분만 1회 재생성하고, 부족하면 프로파일별 최고점으로 보충해 **항상 정확히 3장**을 보장하도록 바꿨습니다.

**현실의 사진.** 최신 폰 사진(7.5MB, 5712×4284)이 Claude 이미지 상한을 넘겨 Stage 1에서 즉사했고, 세로 사진은 EXIF 회전 정보만 있어 누운 옷을 분석할 뻔했습니다. 서버 입구에서 EXIF 회전을 픽셀에 적용하고 4MB/2560px 초과 시 자동 축소하도록 정규화했습니다.

**3D 렌더링.** 컬렉션 그리드에 GLB 여러 개는 무거워 서버가 GLB를 렌더해 투명 배경 정면 PNG를 만들었습니다. 회전각을 바꿔도 렌더가 동일하다는 테스트 실패(파란 픽셀 수가 정확히 같았습니다)로 씬 그래프 변환 미적용을 잡아냈습니다.

## 5. 결과

| 지표 | 값 |
|---|---|
| 파이프라인 | 5단계 + 검증 게이트, 전 구간 REST API |
| 실사진 E2E | 2회 완주 (골든 샘플로 보관, 회귀 벤치마크로 재사용) |
| 브랜드 DB | 제품 이미지 113종, 큐레이션 카탈로그 104종 |

| 1회 원가 | 약 1,300원 (Claude ~190 + Gemini ~290 + Meshy ~840) |
| 소요 시간 | 시작→후보 1~1.5분, 선택→3D 완성 3~4분 |

## 6. 회고

1. **원칙이 기술보다 먼저다.** 갈림길마다 답을 빠르게 해준 건 원칙이었습니다.
2. **환각은 부탁이 아니라 구조로 막는다.** enum으로 잠그면 지어낼 수 없습니다.
3. **AI 심사관도 튜닝 대상이다.** 캘리브레이션에는 회귀를 재는 고정 벤치마크가 필요합니다.
4. **통합 버그의 상당수는 설계 간 충돌이다.** 각자 옳게 동작해도 사용자에게는 오류로 보입니다.
5. **조용한 폴백은 양날의 검이다.** 파이프라인은 지키지만 원인을 가립니다. 폴백에는 반드시 원인 로그를 남겨야 합니다.
